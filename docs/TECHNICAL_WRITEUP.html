EHR Media Intelligence Platform: technical write-up

Local assessment demo. Synthetic data only. Commit history on main: one commit per major task (foundation + ingestion, FHIR R4, AI summaries, semantic search, clinician UI) plus a quota-error fix.

Read first. (1) Live OpenAI verification is a single successful request (synthetic fixture, one attempt, HTTP 200, 975 tokens): it shows the integration works once, not model reliability. (2) Clinical correctness has not been independently validated: no clinician has reviewed any output, and grounding checks show textual traceability only. (3) Authentication and authorization are not implemented. (4) Synthetic-data demo only: do not use with real patient data; not HIPAA-assessed.

What it does

Ingests JSON/CSV/text records; normalizes dates, gender and MRN; detects duplicates and identity conflicts; maps each resolved patient to FHIR R4 (Patient, DocumentReference, DiagnosticReport, Bundle); produces grounded AI summaries (OpenAI behind an interface); supports semantic search; and serves a React clinician search UI.

Architecture

Clean Architecture in a modular monolith (FastAPI): domain (rules, ports) ← application (use cases) ← infrastructure (SQLAlchemy/SQLite, OpenAI, sentence-transformers, fhir.resources) and api (thin routes). An import-direction test enforces the layering, and that fhir.resources and openai stay inside infrastructure. SQLite is the source of truth; the vector index is derived and rebuildable. Patterns: Repository/Unit of Work, Strategy (3 ingestion formats, 2 embedders), one Factory, Adapters, DI.

Key decisions (all in docs/DECISIONS.md, D1–D43)

  • Conservative identity: never merge on name similarity; same MRN + different DOB = conflict; same name+DOB under a new MRN = ambiguous → held for review, with rationale and audit entry.
  • FHIR R4 concepts: per patient a collection Bundle of Patient, DocumentReference (note text as a base64 attachment; context.period = clinical date, date = ingestion time) and DiagnosticReport, linked by urn:uuid references with deterministic ids. Uses fhir.resources.R4B (FHIR 4.3.0, a technical correction of R4 whose elements for these resources were checked as identical to 4.0.1); the package default namespace is R5 and is never used. The library does not enforce value sets or reference resolution, so validation has three layers (library, value-set checks, reference/attachment checks). FHIR state is separate from ingestion status; generation is idempotent by fingerprint. Not a complete FHIR validator.
  • Grounded summaries: the model sees only one patient's clinical text (no name, MRN, DOB, id); every statement needs a verbatim evidence quote and source record ids; deterministic checks cover cited ids, quotes, diagnosis-in-quote, hedging/history/negation, dates/numbers, advice, ≤200 words. Cache key: patient + content hash + prompt version + model. A quote proves traceability, not correctness.
  • AI summary evaluation: 18 deterministic tests on synthetic cases (unsupported claims, dates, identity, attribution, length, schema) plus a human-review rubric that has not been performed; English-only heuristics; the quality indicator is a coverage heuristic. Live result: one request passed all automated checks; no clinician review.
  • Search: SQLite vector store (exact cosine, filters applied before ranking, every hit re-validated) instead of ChromaDB; default all-MiniLM-L6-v2; the lexical embedder is an explicit fallback and there is never a silent substitute (unavailable semantic → 503). Results carry no names/MRNs; the UI fetches them from a separate GET /patients/{id}/display, and detail views use a focused, ownership-checked FHIR resource endpoint rather than the whole Bundle.
  • Trade-offs: SQLite exact-scan vectors over ChromaDB (no extra service, rebuildable, but linear: 130 ms at 20,000 entries, unmeasured beyond); semantic default with an honest lexical fallback (a 1 GB install and 503 until set up, in exchange for never silently degrading); explicit per-patient FHIR/summary/index steps (simple, idempotent, retryable, but not automatic); no authentication, to keep the demo scope honest rather than add a cosmetic mechanism.
  • Error handling: provider/SDK text is never propagated or logged; HTTP 429 insufficient_quota is permanent (one attempt), rate limits/5xx/network errors use bounded retry.

Limitations and deviations

  • Not verified: model reliability or output quality beyond one live request; clinician review of any summary; Windows setup commands; other browsers; automated accessibility/visual tests; contrast.
  • Security: no authn/authz; any caller can read all data; the full-Bundle FHIR endpoint returns whole Patient resources; patient filtering is data scoping, not access control.
  • Deviations from the brief: SQLite vector store instead of ChromaDB; no GET /patients or GET /patients/{id} (display lookup instead); search field is limit (max 5), not top_k; FHIR/summary/index are explicit per-patient calls, not automatic after ingestion.
  • Other: English-only heuristics; quality indicator is a coverage heuristic, not a confidence; no needs_review workflow; no migrations; no CI.
